01Para que serve

Testar um sistema pede dados que conversem entre si: o cadastro que o documento referencia, o contrato vigente na data, o pagamento com o valor da cobrança. Montar isso à mão é lento e não se repete igual.

O Gerador de massa é um app à parte, em repositório próprio e genérico: o usuário modela as entidades, gera massa coerente, envia a uma API de destino cadastrada, acompanha cada requisição e confere o resultado contra um gabarito. Nada no núcleo é específico de um sistema: o domínio entra por pacotes. O SplitHub é o primeiro pacote, construído a partir do docs da API ↗.

Em uma frase

Um cliente sintético configurável: modela, gera, envia, acompanha e confere massa de teste para qualquer API — e já vem com o pacote do SplitHub.

04Núcleo e pacotes

O que é igual para qualquer sistema fica no núcleo. O que é de um sistema — as entidades dele, as regras de negócio, os cenários e a estrutura da API — fica num pacote, instalado no app e declarado pelo destino.

Núcleo · genérico
O que o app sabe fazer
  • Destinos, autenticação, limites e canais
  • Estrutura de APIs: importar, preencher, mapear
  • Modelos de entidade, geradores e regras
  • Cadastros mestres e cenários
  • Envio, monitor, conferência e execuções
Pacote · por domínio
O que um sistema exige
  • Modelos das entidades do domínio
  • Regras de negócio e casos de borda
  • Geradores especializados que usa
  • Esquema do contrato e estrutura padrão
  • Cenários prontos com gabarito
Teste de que o núcleo é genérico

Modelar e mandar massa para uma API que não é o SplitHub sem escrever código. É o critério de pronto do MVP (seção 12).

13Decisões para aprovar

Do núcleo

D-01Tecnologia

Recomendação: TypeScript na interface e no servidor, com PostgreSQL. Um só idioma para esquemas, núcleo e telas.

D-02Onde o app roda

Recomendação: Hospedado, com acesso restrito ao time. O receptor de webhooks precisa de URL pública, e o envio longo não pode depender de uma máquina ligada.

D-03Formato do pacote

Recomendação: Arquivo declarativo (YAML ou JSON) versionado em repositório, importado pelo app. O domínio fica revisável em código, fora do banco.

D-04Regras e geradores sem código livre

Recomendação: Linguagem de expressão segura para regras e campos calculados, sem acesso a rede nem a arquivo. Geradores especializados entram como módulos do app e o pacote os chama por nome — pacote não executa código.

D-05Fonte da estrutura e dos esquemas

Recomendação: Papéis separados. A chamada — rota, método, cabeçalhos, autenticação — vem da collection ou da OpenAPI do destino; o conteúdo do corpo segue o esquema do pacote. Divergência aparece na importação.

D-06Operação sem requisição na estrutura

Recomendação: Usar a operação padrão do pacote, marcada como tal, em vez de bloquear.

D-07Quem envia

Recomendação: Produto e QA. Desenvolvimento usa os mesmos cenários pelo app, sem acesso direto às credenciais.

D-08Retenção

Recomendação: Execuções, massa e registro de requisições por 90 dias; cenários, cadastros e pacotes, sem prazo.

Do pacote SplitHub

D-09Cadastro do comprador

Recomendação: A API pública não cria os estabelecimentos do comprador. No MVP, o pacote gera os dados e um roteiro de cadastro na plataforma; avaliar uma rota de apoio só nos sandboxes.

D-10Guias sem evento

Recomendação: O evento rad.darf_received está no contrato, mas o produto ainda não o emite (PRD de Execução RAD). Consulta periódica a GET /v1/rad/guides, trocando pelo evento quando ele existir.
