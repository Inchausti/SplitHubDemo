API de eventos fiscais

A API pública do SplitHub recebe documentos fiscais e não recebe eventos. Sem eles o produto não sabe que um crédito foi estornado, que um presumido foi pedido ou que um débito mudou de competência. Esta proposta desenha o contrato que falta: seis rotas e um envelope que absorve os dezesseis tipos.

01O buraco no contrato

A API pública tem 25 endpoints em sete páginas — autenticação, fornecedores, contratos, ingestão de DFs com lote de até 500, RAD, automações e garantia de crédito. Nenhum recebe evento fiscal.

O documento entra por POST /v1/documentos-fiscais e a partir daí o produto o trata como algo estável. Não é: entre a emissão e o recolhimento, os eventos mudam valor, competência e estado do crédito. Sem recebê-los, o SplitHub concilia contra uma foto desatualizada e produz divergência onde não há.

Sem o endpointConsequência
Perecimento em trânsito não chegaO produto mantém crédito sobre mercadoria que não existe
Crédito presumido pedido por evento não chegaO valor conciliado é o destacado, e o Fisco vai apurar o presumido
Previsão de entrega atualizada não chegaDébito cobrado na competência errada
Aceite de nota de crédito não chegaAjuste de valor sem rastro de quem consentiu
Transferência por sucessão não chegaCrédito sai da apuração sem explicação
O caminho do evento não passa pelo SplitHub

O ERP registra o evento no ambiente autorizador — SVRS, pelo Web Service NFeRecepcaoEvento. De lá a apuração assistida o consome. O SplitHub não emite evento e não quer emitir: ele precisa saber que o evento existiu, para conciliar o efeito com o saldo que o Fisco devolver. Por isso o endpoint é de importação, e recebe o evento já autorizado.

02O princípio do desenho

São dezesseis tipos com estruturas diferentes. Há três formas de absorver isso, e duas dão errado.

OpçãoComo seriaPor que não
Um endpoint por eventoPOST /v1/eventos/perecimento-fob, e mais quinzeDezesseis rotas para manter. A NT muda — o 211120 foi eliminado na v1.50 — e cada mudança vira mudança de contrato público
Um envelope plano com todos os camposUm objeto com indQuitacao, dPrevEntrega, gPerecimento… todos opcionaisNada é obrigatório e tudo é possível. A validação migra para o servidor e o ERP descobre o erro tarde
Um envelope com discriminadortype decide o formato de detailÉ a proposta. Espelha a própria norma — tpEvento mais detEvento — e o padrão que a API já usa em documentos-fiscais, onde type decide o resto
Espelhar a norma não é preguiça de desenho

O ERP já tem o dado nessa forma: ele montou o XML para enviar à SEFAZ. Pedir outra estrutura obriga o cliente a traduzir duas vezes e cria uma superfície de erro que não precisa existir. O que a API acrescenta é nome legível, tipagem por discriminador e validação na entrada — não uma ontologia nova.

03As rotas
MétodoRotaPara quêResposta

DELETE/v1/eventos-fiscais/{id}Remove o registro de importação enviado por engano204
Não há PATCH, e o DELETE não cancela nada no Fisco

Evento autorizado é imutável. A norma não corrige evento: ela cancela pelo 110001, que é ele próprio um evento. Portanto cancelar, na nossa API, é um POST de um evento do tipo cancelamento — nunca um PATCH nem um DELETE.

O DELETE existe só para desfazer uma importação indevida — o ERP mandou o evento errado para o SplitHub. Não toca no ambiente autorizador, e deve recusar evento que já foi conciliado.

04O envelope

Comum a todos os dezesseis. O que muda é só o detail.

{
  "type":           "apropriacao_credito_presumido",   // nome legível
  "event_code":     "211110",                          // tpEvento da norma
  "access_key":     "41260912345678000190550010000012341123456789",
  "protocol":       "141260000123456",                 // nProtEvento — a prova
  "event_datetime": "2026-09-25T10:15:00-03:00",       // dhEvento
  "sequence":       1,                                 // nSeqEvento
  "author": {
    "tax_id": "12345678000190",                         // CNPJ ou CPF do autor
    "role":   "acquirer"                                // issuer | acquirer | successor | tax_authority
  },
  "authorizer_state": "41",                             // cOrgaoAutor
  "environment":      "production",                     // production | staging — tpAmb
  "detail": { /* formato decidido por type — seção 05 */ }
}
CampoOrigem na normaObrig.Por que está aqui
type—simNome legível, estável entre versões da NT. É o discriminador de detail
event_codetpEventosimO código oficial. Os dois vêm juntos e o servidor valida a coerência — o ERP fala o código, o produto fala o nome
access_keychNFesim44 posições. Liga o evento ao documento e à apuração dos dois órgãos
protocolnProtEventosimA prova de que a SEFAZ autorizou. Evento sem protocolo não produziu efeito e não deve conciliar
event_datetimedhEventosimDefine a janela onde procurar o efeito no saldo
sequencenSeqEventosimCom access_key e event_code, forma a chave natural de idempotência
author.tax_idCNPJ / CPFsimQuem registrou
author.roletpAutorsimMapeia 1, 2, 8 e 5 para nome. Validado contra o papel daquele CNPJ no documento
authorizer_statecOrgaoAutornãoUF do autor. Útil na trilha, dispensável na conciliação
environmenttpAmbnãoEvento de homologação nunca concilia contra apuração de produção
Idempotência sem cabeçalho extra

A tripla access_key + event_code + sequence é única por definição da norma. Reenvio do mesmo evento devolve 200 com o registro existente, não 202 nem duplicata. Não é preciso Idempotency-Key: o domínio já tem chave.

05Os oito formatos de detail

Os dezesseis tipos usam oito estruturas. Quem implementa escreve oito validadores, não dezesseis.

Oito aqui, seis na norma

Os Leiautes agrupam o detEvento em seis formas. A API usa oito porque separa o que a norma junta: a forma escalar vira indicator e date, que têm tipos diferentes; e o 112130 ganha forma própria, porque carrega a perna de estorno que os outros eventos de item não têm. Tipagem mais fina na entrada rejeita mais cedo.

1 · indicator — confirmação binária

Tipos: 112110, 211128, 212110, 212120.

"detail": { "accepted": true }        // indQuitacao / indAceitacao

No 112110 a norma só admite “1”: accepted falso deve ser recusado na entrada.

2 · date — nova competência

Tipo: 112150.

"detail": { "expected_delivery_date": "2026-11-30" }   // dPrevEntrega

3 · items — valor e quantidade por item

Tipos: 112120, 112130, 112140, 211124, 211130, 211140. Até 990 itens.

"detail": {
  "items": [
    {
      "item_number": 1,                    // nItem
      "ibs_amount": 120.00,                // vIBS
      "cbs_amount": 108.00,                // vCBS
      "quantity": 3.0000,                 // gControleEstoque
      "unit": "UN"
    }
  ]
}

Um único formato para os seis: a norma dá nome diferente ao par quantidade/unidade em cada evento — qPerecimento, qImobilizado, qComb, qNaoFornecida, qtde — mas a semântica é a mesma. O type já diz do que se trata.

4 · items_with_reversal — o caso do 112130

Só o perecimento em frete CIF. Acrescenta a segunda perna.

"detail": {
  "items": [
    {
      "item_number": 1,
      "ibs_amount": 120.00, "cbs_amount": 108.00,
      "quantity": 3.0000, "unit": "UN",
      "acquisition_credit_reversal": {    // P30–P32 — só neste evento
        "ibs_amount": 90.00,
        "cbs_amount": 81.00
      }
    }
  ]
}

5 · credit_items — crédito sem quantidade

Tipo: 211150. Afirma destinação, não consumo físico.

"detail": {
  "items": [
    { "item_number": 1, "ibs_credit_amount": 120.00, "cbs_credit_amount": 108.00 }
  ]
}

6 · presumed_credit — o 211110

Único com base, classificação e subgrupos por tributo.

"detail": {
  "items": [
    {
      "item_number": 1,
      "calculation_base": 10000.00,        // vBCCredPres
      "classification_code": "01",         // cCredPres — tabela do Portal
      "ibs": { "rate": 1.00, "amount": 100.00, "suspensive_amount": null },
      "cbs": { "rate": 0.90, "amount":  90.00, "suspensive_amount": null }
    }
  ]
}

ibs e cbs são opcionais e excludentes conforme o código: a tabela cCredPres traz indicadores que vedam ou exigem cada um. O suspensive_amount corresponde a vCredPresCondSus e só vale para a classificação 4, a partir de 2027 na CBS e 2033 no IBS — ver o crédito presumido em detalhe.

7 e 8 · decision e cancellation

// 412120 e 412130 — manifestação do Fisco
"detail": { "granted": false, "reason_code": "1", "reason": "Falta de manifestação de todas as sucessoras" }

// 110001 — cancelamento
"detail": { "cancelled_event_code": "211110", "cancelled_protocol": "141260000123456" }

07Validações na entrada

O valor de um endpoint tipado está em recusar cedo. Estas são as regras que o contrato deve aplicar antes de aceitar.

#RegraCódigo
V-01event_code existe no catálogo da NT vigenteevent_code_unknown
V-02type corresponde ao event_codetype_code_mismatch
V-03detail tem o formato do typedetail_shape_invalid
V-04access_key com 44 posições e dígito verificador válidoaccess_key_invalid
V-05protocol presente — evento sem autorização não entraprotocol_required
V-06author.role compatível com o papel do tax_id no documentoauthor_role_mismatch
V-07Eventos de item: item_number existe no DF, e não se repeteitem_not_found · item_duplicated
V-08Máximo de 990 itens em detail.itemsitems_limit_exceeded
V-09apropriacao_credito_presumido recusado em documento modelo 65presumed_credit_not_allowed
V-10cancelamento não pode cancelar outro cancelamentocannot_cancel_cancellation
V-11cancelamento: autor igual ao do evento canceladocancel_author_mismatch
V-12pagamento_integral com accepted falsoindicator_value_invalid
V-13Duplicidade por access_key + event_code + sequencedevolve 200 com o existente
O documento pode não existir ainda

V-04 e V-07 pressupõem o DF na base. Evento que chega antes do documento é caso normal, não erro: o endpoint aceita com 202 e status aguardando_documento, e reavalia quando o DF entrar. Descartar produz crédito apropriado sobre documento que não existe.

08Ciclo de vida e webhooks

O evento entra, correlaciona com o documento e espera o saldo se mover na apuração. O GET devolve onde ele está.

statusSignifica
recebidoAceito e validado
aguardando_documentoO DF ainda não chegou — fica na fila de correlação
correlacionadoLigado ao documento e aos itens
conciliadoO saldo na apuração moveu no valor declarado
divergenteO saldo moveu em valor diferente, ou não moveu quando deveria
nao_atribuivelMais de um evento na mesma janela de coleta — o delta fecha em montante, sem atribuição
canceladoUm cancelamento válido o alcançou

Três eventos de webhook, no envelope que a API já usa — event, created_at, data:

EventoQuando dispara
evento_fiscal.correlacionadoO evento encontrou o documento, com o efeito calculado nos itens
evento_fiscal.conciliadoA apuração confirmou o efeito
evento_fiscal.divergenteNão confirmou — vai junto o motivo e a ocorrência aberta
Depende da decisão D-01

O produto emite hoje credito.registrado, apropriado, utilizado e glosado; o contrato público define credito.status_alterado e debito.status_alterado. Os dois contratos convivem sem decisão desde a auditoria. Os três nomes acima seguem o padrão do contrato público, mas não devem ser publicados antes de D-01 — ou nascem já em conflito. Ver D-01 na auditoria.

09Erros e lote

Resposta individual, 202, no formato que a ingestão de DFs já usa:

{
  "id": "evt_9c41b7de",
  "status": "recebido",
  "type": "apropriacao_credito_presumido",
  "event_code": "211110",
  "access_key": "4126…6789",
  "created_at": "2026-09-25T13:02:11.000Z"
}

No lote, o que vale é a recusa item a item: um evento inválido não derruba os outros 499.

{
  "batch_id": "evtbatch_3k9m2x",
  "status": "processing",
  "total_events": 500,
  "accepted": 498,
  "rejected": 2,
  "events": [
    { "index": 0, "id": "evt_9c41b7de", "status": "recebido" },
    { "index": 17, "status": "rejected",
      "error": { "code": "item_not_found", "message": "Item 4 não existe no documento",
                 "field": "detail.items[0].item_number" } }
  ]
}

O objeto de erro — code, message, field — é proposta desta página: a documentação pública atual não publica formato de erro. Se houver um padrão interno, ele manda.
