Gerador de massa de dados

Um app genérico e interativo para montar o contexto de dados mestre de um ambiente de teste com várias integrações e, a partir dele, gerar massa para cada barramento — enviando ao sistema testado como cliente ou emulando os entes com que ele se integra. O SplitHub é o primeiro pacote de domínio.

01Para que serve

Testar um sistema pede dados que conversem entre si: o cadastro que o documento referencia, o contrato vigente na data, o pagamento com o valor da cobrança. Montar isso à mão é lento e não se repete igual.

O Gerador de massa é um app à parte, em repositório próprio e genérico. Na v3.0 ele passa a trabalhar por ambiente de teste: um ambiente reúne as várias integrações de um sistema — a API que ele expõe e as APIs de terceiros com que ele conversa —, um único conjunto de dados mestre e o contexto de massa gerado a partir deles. Cada integração recebe a sua parte do mesmo contexto: o app envia como cliente para a API do sistema testado e emula os entes do outro lado, gerando os eventos que eles produziriam. Nada no núcleo é específico de um sistema: o domínio entra por pacotes. O SplitHub é o primeiro pacote, construído a partir do docs da API ↗.

Em uma frase

Um contexto de dados mestre por ambiente e uma massa coerente para cada barramento: o mesmo fornecedor, o mesmo contrato e o mesmo documento aparecem na API do sistema e nos eventos dos entes emulados.

04Núcleo e pacotes

O que é igual para qualquer sistema fica no núcleo. O que é de um sistema — as entidades dele, as regras de negócio, os cenários e a estrutura da API — fica num pacote, instalado no app e declarado pelo destino.

  • Envio, emulação de entes, monitor, conferência e execuções

Por que isso importa

O sistema testado só se comporta como em produção quando as duas pontas falam do mesmo documento. Gerar o contexto uma vez e projetá-lo em cada integração garante que a chave, o fornecedor e os valores sejam os mesmos dos dois lados — e permite testar justamente quando não são.

08Integrações e biblioteca de APIs

Collections e environments ficam guardados numa biblioteca de APIs, independentes das integrações. Uma integração junta uma collection e um environment da biblioteca num ambiente, com um papel. O mesmo contrato serve a vários ambientes: sandbox e homologação usam a mesma collection com environments diferentes.

O que a biblioteca guardaComo
CollectionO arquivo original inteiro (Postman v2.1): pastas, requisições, exemplos de resposta e scripts — que não rodam. Uma versão a cada importação, com o que mudou.
EnvironmentO arquivo original sem os valores secretos: cada segredo vai para o cofre e fica no arquivo como referência. Uma versão a cada importação.
Origem e usoQuem importou, quando, o nome do arquivo, o hash e as integrações que usam cada versão.
AgnósticoQualquer collection Postman v2.1, de qualquer sistema; OpenAPI 3 na Fase 2.

A integração e a sua estrutura de APIs são montadas por dois caminhos, que se combinam: importar e depois ajustar à mão, ou preencher à mão e depois importar por cima, vendo o que muda.

Integração de ente emulado

A collection é a das rotas que o sistema testado expõe para receber o que o ente manda. Enquanto a rota não existe, a integração fica com o status Aguardando rota, e os eventos são gerados e guardados mesmo assim.

Muitos sistemas dependem de terceiros que não estão no sandbox: órgãos de governo, bancos, adquirentes. O app faz o papel desses terceiros — gera, a partir do contexto, os eventos que eles produziriam e os entrega ao sistema testado.

Modelo neutro de evento

Enquanto o sistema testado não expõe as rotas, o pacote descreve os eventos num modelo neutro: tipo, registro, tributo, valores e data. Quando a collection das rotas chega, cada tipo de evento é ligado a uma operação e o corpo passa a seguir o contrato importado.

Fora desta versão

Responder como a API do ente — o sistema testado consultando o app no lugar do órgão — fica para quando um sistema precisar desse modo (D-13).

15Decisões para aprovar

Do núcleo

D-01Tecnologia

Recomendação: TypeScript na interface e no servidor, com PostgreSQL. Um só idioma para esquemas, núcleo e telas.

D-02Onde o app roda

Recomendação: Hospedado, com acesso restrito ao time. O receptor de webhooks precisa de URL pública, e o envio longo não pode depender de uma máquina ligada.

D-03Formato do pacote

Recomendação: Arquivo declarativo (YAML ou JSON) versionado em repositório, importado pelo app. O domínio fica revisável em código, fora do banco.

D-04Regras e geradores sem código livre

Recomendação: Linguagem de expressão segura para regras e campos calculados, sem acesso a rede nem a arquivo. Geradores especializados entram como módulos do app e o pacote os chama por nome — pacote não executa código.

D-05Fonte da estrutura e dos esquemas

Recomendação: Papéis separados. A chamada — rota, método, cabeçalhos, autenticação — vem da collection ou da OpenAPI do destino; o conteúdo do corpo segue o esquema do pacote. Divergência aparece na importação.

D-06Operação sem requisição na estrutura

Recomendação: Usar a operação padrão do pacote, marcada como tal, em vez de bloquear.

D-07Quem envia

Recomendação: Produto e QA. Desenvolvimento usa os mesmos cenários pelo app, sem acesso direto às credenciais.

D-08Retenção

Recomendação: Execuções, massa e registro de requisições por 90 dias; cenários, cadastros e pacotes, sem prazo.

Do pacote SplitHub

D-09Cadastro do comprador

Recomendação: A API pública não cria os estabelecimentos do comprador. No MVP, o pacote gera os dados e um roteiro de cadastro na plataforma; avaliar uma rota de apoio só nos sandboxes.

D-10Guias sem evento

Recomendação: O evento rad.darf_received está no contrato, mas o produto ainda não o emite (PRD de Execução RAD). Consulta periódica a GET /v1/rad/guides, trocando pelo evento quando ele existir.

Da v3.0

D-11Ambiente como raiz

Recomendação: Toda integração, todo dado mestre e todo contexto pertencem a um ambiente. A biblioteca de APIs fica fora dos ambientes, para o mesmo arquivo servir a vários.

D-12Guardar os arquivos originais

Recomendação: Guardar a collection inteira e o environment sem os valores secretos, com versão. Substitui a regra da v2.0 de não guardar o arquivo; os segredos continuam só no cofre.

D-13Como o ente emulado entrega Decidido

Decidido em 20/10/2026: o app gera os eventos dos entes a partir dos dados mestre do contexto e os entrega nas rotas que o sistema testado expõe. O SplitHub ainda não tem essas rotas: o time vai entregá-las, e até lá os eventos ficam guardados, aguardando rota. Responder como a API do ente fica para a Fase 2.

D-14Formato do evento até a rota existir

Recomendação: Modelo neutro descrito no pacote — tipo, registro, tributo, valores e data —, mapeado para o contrato quando a collection das rotas chegar.

D-15Tempo simulado

Recomendação: Relógio por contexto, avançado pelo usuário, com a opção de entregar tudo de uma vez. Nenhum teste espera dias reais.

D-16Casos correlacionados da primeira entrega (pacote SplitHub)
