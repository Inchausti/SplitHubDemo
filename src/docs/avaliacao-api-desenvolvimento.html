Avaliação da API proposta pelo desenvolvimento

A proposta de endpoints entregue pelo time de desenvolvimento, lida contra o docs da plataforma. Cada gap vem ligado ao requisito de negócio que o justifica — o que falta para o docs operar, o que diverge, o que não faz sentido no contexto, e o que a proposta faz melhor e deveria subir para o docs.

A proposta do time é tecnicamente mais madura que o docs em várias convenções — OAuth 2.0 com escopos, idempotência, paginação por cursor, inativar em vez de apagar. Mas ela não sustenta a operação que o docs descreve. O mapa de integração do docs classifica três integrações como essenciais — documentos fiscais, DARF RAD e comprovante de pagamento —, e as três estão quebradas na proposta:

  • Documentos fiscais: não há envio de documento por API, só por arquivo — e o arquivo não tem endpoint de envio. Depois de confirmado, o documento não pode ser consultado. Requisito: RF-ING-001 a 003.
  • DARF RAD: a guia não chega ao ERP — não há evento liberado, e o objeto Guia não tem código de barras, PIX nem PDF. Requisito: RF-PAG-050 a 054 e RF-EXR-022.
  • Comprovante: a proposta aceita um id de arquivo, sem valor pago nem data. Requisito: Pagamentos §12, que reproduz o payload do docs.

Duas incompatibilidades quebravam qualquer integração escrita pelo docs logo na primeira chamada — dinheiro como texto, resolvida pelo docs v1.1.0, e CNPJ só numérico, ainda aberta. E uma lacuna está nos dois documentos: o contrato não tem método de pagamento, e nenhum dos dois conhece o split payment, que é o método padrão do produto.

Cada gap da seção 04 traz o requisito de negócio que o sustenta, com link para o PRD e para a página do docs. Dos 36, 33 têm requisito escrito nos PRDs; os outros 3 são de convenção técnica ou só do docs, e estão marcados assim.

Aceite de 05/10/2026

Dos onze pontos em que a proposta é melhor que o docs (seção 06), dez foram aceitos. 9 já estão no docs v1.1.0 — commit ccf91f3, publicado nos repositórios Inchausti/SplithubDocs e split-hubhq/docs —, o item 8 tem proposta de envio de arquivo em aprovação, e o item 11 não foi aceito. Com isso, 3 gaps deixam de existir e outros seis ficam reduzidos ou encaminhados; cada cartão da seção 04 diz o que mudou.

04Gaps, com o requisito de negócio de cada um

36 itens — 10 críticos, 9 altos, 12 médios e 5 baixos. Em cada cartão: o que o docs pede e a proposta não entrega, o requisito de negócio que justifica a cobrança — com link para o PRD —, o efeito na operação e a recomendação.

Transversal

G-01CríticoValores monetários: o docs manda número, a proposta recusa número
Resolvido no docs v1.1.0 O docs adotou o texto decimal em todos os recursos (Valores monetários ↗). Sem período de transição: nenhum cliente estava integrado.
Docs × proposta

A proposta só aceita dinheiro como texto decimal e responde 400 a "total_value": 120000.00. O docs usa número em todos os exemplos — contrato, itens, base, IBS e CBS, guias.

Docs · Ingestão DFs ↗ · Docs · Contratos ↗
Requisito de negócio
  • Ingestão §15 — O contrato de entrada — em produção o documento chega pelo contrato publicado, com os campos de valor do docs
  • Contratos §14 — O contrato vindo do ERP — em produção o contrato chega do ERP por /v1/contratos, com total_value
  • RF-ING-001 (Ingestão) — o sistema deve aceitar documentos por API

Por que é requisito: Os PRDs adotaram o contrato publicado como a fronteira de produção. Se a API recusa o formato do docs, nenhum documento nem contrato entra.

Efeito na operação Toda integração escrita pelo docs falha na primeira chamada.
Recomendação Decidir o formato. Se for texto — tecnicamente melhor —, reescrever o docs e aceitar os dois formatos por um período de transição.
G-02CríticoCNPJ alfanumérico recusado
Docs × proposta

A proposta valida CNPJ com ^\d{14}$ no fornecedor e nas guias. O docs aceita o CNPJ alfanumérico.

Docs · Fornecedores ↗ · Docs · Contratos ↗
Requisito de negócio
  • Contratos §14 — O contrato vindo do ERP — "CNPJ alfanumérico, pela IN RFB 2.229/2024, vigente desde 27/07/2026"
  • RN-FORN-01 (Fornecedor) — o CNPJ é a identidade do fornecedor: liga emitente, documento, contrato e trilha
  • RF-FORN-010 (Fornecedor) — o cadastro deve validar o dígito verificador do CNPJ

Por que é requisito: O CNPJ é a chave de tudo. Recusar o formato vigente impede o vínculo do fornecedor novo com as notas dele.

Efeito na operação Fornecedor com CNPJ novo não cadastra, e as notas dele não têm onde se vincular.
Recomendação Aceitar 12 posições alfanuméricas mais 2 dígitos verificadores, validando o dígito.
G-03AltoNão há como dizer qual estabelecimento do grupo é o comprador
Docs × proposta

Na proposta, a empresa vem do token e não existe parâmetro de empresa. O docs tem buyer_cnpj no contrato e acquisition_cnpj nos eventos de RAD.

Docs · Contratos ↗ · Docs · RAD ↗
Requisito de negócio
  • Contratos §14 — O contrato vindo do ERP — o contrato tem "as duas pontas": buyer_cnpj e supplier_cnpj
  • RN-ORG-01 (Organização) — o DF de entrada só é associado ao grupo se o CNPJ destinatário estiver cadastrado e ativo
  • RN-CRE-16 (Crédito) — o filtro por CNPJ inclui todos os CNPJs do mesmo grupo
  • RF-EXR-011 (Execução RAD) — a política por CNPJ inclui só notas cujo CNPJ comprador esteja na lista

Por que é requisito: O produto opera grupos com vários CNPJs, e a Execução RAD orquestra por CNPJ comprador. Sem esse dado na API, a escolha da política não pode ser verificada pelo ERP.

Efeito na operação Contrato, crédito e guia ficam sem o CNPJ comprador; a filial não é filtrável nem auditável pela API.
Recomendação buyer_tax_id no contrato, e filtro por CNPJ comprador em créditos e guias.
G-04MédioFormato de erro diferente, e sem o campo que falhou
Docs × proposta

O docs responde {error, message}; a proposta, {error_code, message}, e põe o campo com problema no texto de message — que ela mesma proíbe de ser lido por máquina.

Docs · Autenticação ↗
Requisito de negócio
  • RN-ING-07 (Ingestão) — a recusa é informativa, nunca silenciosa: registra qual verificação falhou e por quê
  • RF-ING-012 (Ingestão) — o documento recusado deve registrar qual verificação falhou
  • Integrações §12 — Segurança e lacunas da API — lacuna "Sem códigos de erro HTTP": documentar 400, 401, 404, 409 e 422 com corpo padronizado

Por que é requisito: A regra pede que a recusa diga o que falhou. Sem o campo estruturado, o ERP não corrige sozinho.

Efeito na operação Em lote e em formulário, o integrador não consegue apontar o campo errado.
Recomendação Padronizar {error_code, message, field}.
G-05MédioIdioma das rotas e dos campos
Docs × proposta

O docs usa rotas em português (/fornecedores, /contratos, /documentos-fiscais) e campos em inglês. A proposta usa rotas em inglês e mistura os dois idiomas no mesmo objeto: valor, saldo, used_value, appropriated_at.

Docs · Visão geral ↗
Requisito de negócio
  • RF-INT-003 (Integrações) — a tela de Integrações mostra ao cliente "os caminhos reais da API"
  • RF-ING-001 (Ingestão) — o requisito cita literalmente POST /v1/documentos-fiscais

Por que é requisito: O produto e os PRDs já mostram ao cliente as rotas do docs. Se a API usar outras, a tela ensina o caminho errado.

Efeito na operação Nenhuma rota do docs funciona na proposta, e o cliente aprende dois vocabulários.
Recomendação Decidir um idioma por camada e aplicar no docs, nos PRDs e na tela de Integrações.
G-06MédioEndereços e ambientes não fecham
Docs × proposta

O docs publica sandbox-api.splithub.com.br/v1 e api.splithub.com.br/v1. A proposta tem só homologação em splithub.app.br, produção "a definir", e o token fora do /v1.

Docs · Visão geral ↗
Requisito de negócio
  • RF-INT-004 (Integrações) — a conexão deve declarar produção ou sandbox, com credencial live ou test
  • Integrações §12 — Segurança e lacunas da API — lacuna "Sem ambiente de testes"

Por que é requisito: O produto separa produção e sandbox pela credencial; a API precisa dos dois endereços para isso valer.

Efeito na operação O cliente não sabe para onde apontar.
Recomendação Fixar os endereços e publicar nos dois documentos.
G-07BaixoPaginação com três convenções
Resolvido no docs v1.1.0 O docs adotou page/page_size e cursor (Paginação ↗).
Docs × proposta

O docs usa page/limit e page/per_page; a proposta, page/page_size e cursor nas coleções grandes.

Docs · Fornecedores ↗ · Docs · Ingestão DFs ↗
Requisito de negócio

Sem requisito de negócio nos PRDs.

Por que é requisito: Convenção técnica, sem requisito de negócio. O cursor da proposta é melhor.

Efeito na operação Pequeno.

G-09AltoEscopos não cobrem o docs
Parcial no docs v1.1.0 O docs publicou a tabela de escopos, com dfs:read, dfs:write e webhooks:write (Escopos ↗). A proposta ainda precisa criá-los.
Docs × proposta

Faltam escopos para envio de documento por API, comprovante RAD estruturado, débito, inscrição em webhook e automações. O PRD chama o escopo de ingestão de dfs:write; a proposta, de ingestions:write.

Docs · Autenticação ↗
Requisito de negócio
  • RN-INT-05 (Integrações) — chamada fora do escopo retorna 403: "o escopo só vale se for aplicado"
  • RF-ING-001 (Ingestão) — documento por API "autenticado com escopo dfs:write"
  • RF-INT-014 (Integrações) — escopos destrutivos não vêm marcados por padrão

Por que é requisito: Sem escopo declarado, o recurso não tem como ser autorizado nem negado.

Efeito na operação Mesmo implementados, esses recursos não teriam como ser liberados por credencial.
Recomendação Ampliar a lista de escopos com cada endpoint que faltar, e alinhar os nomes com o PRD.

Contratos

G-14CríticoContrato sem método de pagamento e sem prazo
Docs × proposta

A ingestão do docs diz que o documento pode "sobrescrever os parâmetros de contrato (método de pagamento e prazo)". Mas nem o contrato do docs nem o da proposta têm esses campos — só rad_eligible.

Docs · Contratos ↗ · Docs · Ingestão DFs ↗
Requisito de negócio
  • RF-CTR-001 (Contratos) — o contrato deve registrar CNPJ, vigência, modelo de operação e prazo de pagamento
  • RF-CTR-002 (Contratos) — o método é um enum de três valores — split, rad, fornecedor — com fonte única
  • RF-CTR-013 (Contratos) — o contrato resolvido determina o método do registro fiscal gerado
  • RN-CTR-15 (Contratos) — prazo de 1 a 360 dias
  • RN-ING-04 (Ingestão) — o método do registro fiscal vem do contrato vigente na data de emissão

Por que é requisito: É o contrato que diz quem recolhe. Sem método no contrato, a plataforma não sabe se gera guia RAD, se o recolhimento é do fornecedor ou por split.

Efeito na operação O RAD por contrato não funciona, e o crédito nasce sem método.
Recomendação payment_method (split_payment, rad, fornecedor) e payment_term_days no contrato — nos dois documentos.
G-15AltoSituação digitada, e não derivada da vigência
Parcial no docs v1.1.0 O docs passou a situação a ato, por PATCH …/status, e a vigência a cálculo, em term_status (Contratos ↗). Falta, nos dois documentos, o 409 para vigência sobreposta.
Docs × proposta

Docs e proposta guardam a situação (active, suspended…) como dado do cliente. A proposta só valida número de contrato repetido.

Docs · Contratos ↗
Requisito de negócio
  • RN-CTR-03 (Contratos) — o status é calculado da vigência a cada leitura; nunca armazenado
  • RF-CTR-003 (Contratos) — produz ativo, a_iniciar, encerrado ou invalido com a passagem do tempo
  • RN-CTR-02 (Contratos) — um contrato vigente por CNPJ: vigências não podem se sobrepor
  • RF-CTR-022 (Contratos) — o cadastro rejeita vigência sobreposta a contrato do mesmo CNPJ

Por que é requisito: Com dois contratos vigentes, o método da nota fica ambíguo; com status digitado, contrato vencido segue valendo.

Efeito na operação Contrato vencido segue active; dois contratos vigentes deixam o método da nota ambíguo.
Recomendação Vigência derivada das datas; suspensão e cancelamento como atos; 409 para vigência sobreposta.

05Endpoints que não fazem sentido no contexto

Seis pontos da proposta — um deles também presente no docs — que vão contra uma regra de negócio ou não têm caso de uso de integração.

N-01Régua de cobrança configurada por API
GET/POST /v1/contracts/{id}/billing-rules · PUT · PATCH …/active
Por que não faz sentido

O docs configura automação no portal, e a API só recebe o retorno. Pela proposta, o ERP escreve o e-mail que vai ao fornecedor em nome da organização, sem aprovação. A régua é presa ao contrato, mas dispara pelo "vencimento" de um objeto que a proposta não diz qual é; e não tem condição de disparo, então cobra fornecedor que já pagou.

Requisito de negócio
  • RN-AUT-08 (Automações) — cobrar fornecedor é ato externo; o texto sai em nome da organização — por isso alterar template pede aprovação
  • RN-AUT-07 (Automações) — alteração de parâmetro exige justificativa
  • RF-AUT-011 (Automações) — cada etapa define dia relativo, canal, condição e assunto
  • Automações §16 — Webhook e eventos de automação — "em produção o ERP se inscreve e recebe os eventos" — não configura
Recomendação Tirar da API pública; a régua fica no produto, como o docs prevê. Se houver caso de uso de ERP, só leitura.
N-02Credencial de fornecedor pagando guia RAD
escopo supplier_guias:pay · "credenciais de fornecedor acessam apenas as próprias guias"
Por que não faz sentido

No RAD quem recolhe é o adquirente — o cliente da API. O fornecedor não paga essa guia. Abrir a API corporativa a credenciais de terceiros amplia a superfície de ataque sem caso de uso no docs.

Requisito de negócio
  • RN-PAG-15 (Pagamentos) — módulo oculto ao perfil Fornecedor: "RAD é operação do adquirente"
  • RN-POR-03 (Portal do fornecedor) — quem concede e revoga acesso de fornecedor é o adquirente
  • RN-POR-01 (Portal do fornecedor) — a filtragem do que o fornecedor vê é do servidor, nunca da tela
Recomendação Remover o papel de fornecedor da API. Se o produto quiser fornecedor na API, é decisão separada.
N-03Ranking de fornecedores por crédito
GET /v1/credits/suppliers/top
Por que não faz sentido

É um gráfico do painel. Devolve o nome do fornecedor em texto, não o id — não dá para cruzar com nada no ERP. O docs não tem nada parecido.

Requisito de negócio
  • RF-CRE-059 (Crédito) — o Top 10 é componente de tela, com barra segmentada e score de 0 a 10
Recomendação Remover. Análise vai pela exportação para BI, que o docs lista como integração opcional.
N-04Indicadores de painel expostos como API
/v1/credits/composition · /v1/credits/deadlines · /v1/supplier-invoices/guias/totals · /v1/ingestions/metrics
Por que não faz sentido

São agregados de tela. O ERP calcula a partir das listagens; mantê-los obriga a garantir que a API e a tela somem igual. E /v1/ingestions/metrics colide com /v1/ingestions/{id}.

Requisito de negócio
  • RF-PAG-003 (Pagamentos) — o recorte da tabela e dos indicadores tem de ser idêntico — uma terceira soma na API é mais um ponto de divergência
  • RN-CRE-15 (Crédito) — os indicadores dependem dos filtros da tela
Recomendação Manter só os que tiverem caso de uso de integração declarado; o resto vai para a exportação analítica.
N-05Separar "dfe" de "nfse" no envio
POST /v1/ingestions — campo kind
Por que não faz sentido

No docs, NFS-e é um dos 14 tipos, com o mesmo tratamento dos outros. A separação sugere dois fluxos sem razão escrita.

Requisito de negócio
  • Ingestão §15 — O contrato de entrada — o contrato aceita 14 tipos, NFS-e entre eles
Recomendação Trocar kind por type e model (G-21).
N-06Representante fiscal com RG e órgão emissor — no docs e na proposta
…/representatives
Por que não faz sentido

O docs diz que o representante é "essencial para validação de documentos fiscais e cálculo de créditos". Nenhuma regra do produto usa o representante para isso. Guardar RG de pessoa física sem finalidade definida esbarra no princípio da necessidade da LGPD.

Requisito de negócio
  • RN-FORN-08 (Fornecedor) — a única entidade de pessoa no produto é o acesso ao portal, por pessoa e CNPJ
Recomendação Definir a finalidade — por exemplo, o acesso ao portal — ou retirar RG e órgão emissor.
