API de eventos fiscais

A API pública do SplitHub recebe documentos fiscais e não recebe eventos. Sem eles o produto não sabe que um crédito foi estornado, que um presumido foi pedido ou que um débito mudou de competência. Esta proposta desenha o contrato que falta: seis rotas e um envelope que absorve os dezesseis tipos.

01O buraco no contrato

A API pública tem 25 endpoints em sete páginas — autenticação, fornecedores, contratos, ingestão de DFs com lote de até 500, RAD, automações e garantia de crédito. Nenhum recebe evento fiscal.

O documento entra por POST /v1/documentos-fiscais e a partir daí o produto o trata como algo estável. Não é: entre a emissão e o recolhimento, os eventos mudam valor, competência e estado do crédito. Sem recebê-los, o SplitHub concilia contra uma foto desatualizada e produz divergência onde não há.

Sem o endpointConsequência
Perecimento em trânsito não chegaO produto mantém crédito sobre mercadoria que não existe
Crédito presumido pedido por evento não chegaO valor conciliado é o destacado, e o Fisco vai apurar o presumido
Previsão de entrega atualizada não chegaDébito cobrado na competência errada
Aceite de nota de crédito não chegaAjuste de valor sem rastro de quem consentiu
Transferência por sucessão não chegaCrédito sai da apuração sem explicação
O caminho do evento não passa pelo SplitHub

O ERP registra o evento no ambiente autorizador — SVRS, pelo Web Service NFeRecepcaoEvento. De lá a apuração assistida o consome. O SplitHub não emite evento e não quer emitir: ele precisa saber que o evento existiu, para conciliar o efeito com o saldo que o Fisco devolver. Por isso o endpoint é de importação, e recebe o evento já autorizado.

Esta API é a única porta de entrada dos eventos (D-21, 30/09/2026). Quem envia é o cliente, a partir do ERP — os eventos que ele mesmo registra, série 211xxx — e do sistema fiscal — os que o fornecedor registra sobre documentos em que o cliente é parte, série 112xxx.

02O princípio do desenho

São dezesseis tipos com estruturas diferentes. Há três formas de absorver isso, e duas dão errado.

OpçãoComo seriaPor que não
Um endpoint por eventoPOST /v1/eventos/perecimento-fob, e mais quinzeDezesseis rotas para manter. A NT muda — o 211120 foi eliminado na v1.50 — e cada mudança vira mudança de contrato público
Um envelope plano com todos os camposUm objeto com indQuitacao, dPrevEntrega, gPerecimento… todos opcionaisNada é obrigatório e tudo é possível. A validação migra para o servidor e o ERP descobre o erro tarde
Um envelope com discriminadortype decide o formato de detailÉ a proposta. Espelha a própria norma — tpEvento mais detEvento — e o padrão que a API já usa em documentos-fiscais, onde type decide o resto
Espelhar a norma não é preguiça de desenho

O ERP já tem o dado nessa forma: ele montou o XML para enviar à SEFAZ. Pedir outra estrutura obriga o cliente a traduzir duas vezes e cria uma superfície de erro que não precisa existir. O que a API acrescenta é nome legível, tipagem por discriminador e validação na entrada — não uma ontologia nova.

03As rotas
MétodoRotaPara quêResposta

DELETE/v1/eventos-fiscais/{id}Remove o registro de importação enviado por engano204
Não há PATCH, e o DELETE não cancela nada no Fisco

Evento autorizado é imutável. A norma não corrige evento: ela cancela pelo 110001, que é ele próprio um evento. Portanto cancelar, na nossa API, é um POST de um evento do tipo cancelamento — nunca um PATCH nem um DELETE.

O DELETE existe só para desfazer uma importação indevida — o ERP mandou o evento errado para o SplitHub. Não toca no ambiente autorizador, e deve recusar evento que já foi conciliado.

04O envelope

Comum a todos os dezesseis. O que muda é só o detail.

{
  "type":           "apropriacao_credito_presumido",   // nome legível
  "event_code":     "211110",                          // tpEvento da norma
  "access_key":     "41260912345678000190550010000012341123456789",
  "protocol":       "141260000123456",                 // nProtEvento — a prova
  "event_datetime": "2026-09-25T10:15:00-03:00",       // dhEvento
  "sequence":       1,                                 // nSeqEvento
  "author": {
    "tax_id": "12345678000190",                         // CNPJ ou CPF do autor
    "role":   "acquirer"                                // issuer | acquirer | successor | tax_authority
  },
  "authorizer_state": "41",                             // cOrgaoAutor
  "environment":      "production",                     // production | staging — tpAmb
  "detail": { /* formato decidido por type — seção 05 */ }
}

type—simNome legível, estável entre versões da NT. É o discriminador de detail
event_codetpEventosimO código oficial. Os dois vêm juntos e o servidor valida a coerência — o ERP fala o código, o produto fala o nome
access_keychNFesim44 posições. Liga o evento ao documento e à apuração dos dois órgãos

Idempotência sem cabeçalho extra

A tripla access_key + event_code + sequence é única por definição da norma. Reenvio do mesmo evento devolve 200 com o registro existente, não 202 nem duplicata. Não é preciso Idempotency-Key: o domínio já tem chave.

05Os oito formatos de detail

Os dezesseis tipos usam oito estruturas. Quem implementa escreve oito validadores, não dezesseis.

Oito aqui, seis na norma

Os Leiautes agrupam o detEvento em seis formas. A API usa oito porque separa o que a norma junta: a forma escalar vira indicator e date, que têm tipos diferentes; e o 112130 ganha forma própria, porque carrega a perna de estorno que os outros eventos de item não têm. Tipagem mais fina na entrada rejeita mais cedo.

1 · indicator — confirmação binária

Tipos: 112110, 211128, 212110, 212120.

"detail": { "accepted": true }        // indQuitacao / indAceitacao

No 112110 a norma só admite “1”: accepted falso deve ser recusado na entrada.

2 · date — nova competência

Tipo: 112150.

"detail": { "expected_delivery_date": "2026-11-30" }   // dPrevEntrega

3 · items — valor e quantidade por item

Tipos: 112120, 112140, 211124, 211130, 211140. Até 990 itens.

"detail": {
  "items": [
    {
      "item_number": 1,                    // nItem
      "ibs_amount": 120.00,                // vIBS
      "cbs_amount": 108.00,                // vCBS
      "quantity": 3.0000,                 // gControleEstoque
      "unit": "UN"
    }
  ]
}

Um único formato para os seis: a norma dá nome diferente ao par quantidade/unidade em cada evento — qPerecimento, qImobilizado, qComb, qNaoFornecida, qtde — mas a semântica é a mesma. O type já diz do que se trata.

4 · items_with_reversal — o caso do 112130

Só o perecimento em frete CIF. Acrescenta a segunda perna.

"detail": {
  "items": [
    {
      "item_number": 1,
      "ibs_amount": 120.00, "cbs_amount": 108.00,
      "quantity": 3.0000, "unit": "UN",
      "acquisition_credit_reversal": {    // P30–P32 — só neste evento
        "ibs_amount": 90.00,
        "cbs_amount": 81.00
      }
    }
  ]
}

5 · credit_items — crédito sem quantidade

Tipo: 211150. Afirma destinação, não consumo físico.

"detail": {
  "items": [
    { "item_number": 1, "ibs_credit_amount": 120.00, "cbs_credit_amount": 108.00 }
  ]
}

6 · presumed_credit — o 211110

Único com base, classificação e subgrupos por tributo.

"detail": {
  "items": [
    {
      "item_number": 1,
      "calculation_base": 10000.00,        // vBCCredPres
      "classification_code": "01",         // cCredPres — tabela do Portal
      "ibs": { "rate": 1.00, "amount": 100.00, "suspensive_amount": null },
      "cbs": { "rate": 0.90, "amount":  90.00, "suspensive_amount": null }
    }
  ]
}

ibs e cbs são opcionais e excludentes conforme o código: a tabela cCredPres traz indicadores que vedam ou exigem cada um. O suspensive_amount corresponde a vCredPresCondSus e só vale para a classificação 4, a partir de 2027 na CBS e 2033 no IBS — ver o crédito presumido em detalhe.

7 e 8 · decision e cancellation

// 412120 e 412130 — manifestação do Fisco
"detail": { "granted": false, "reason_code": "1", "reason": "Falta de manifestação de todas as sucessoras" }

// 110001 — cancelamento
"detail": { "cancelled_event_code": "211110", "cancelled_protocol": "141260000123456" }

O documento pode não existir ainda

V-04 e V-07 pressupõem o DF na base. Evento que chega antes do documento é caso normal, não erro: o endpoint aceita com 202 e fase aguardando_documento, e reavalia quando o DF entrar. Descartar produz crédito apropriado sobre documento que não existe.

08Ciclo de vida, conciliação e webhooks

A situação de um evento tem duas camadas, e a resposta da API separa as duas. A fase da ação é do evento: em que ponto do ciclo capturar, planejar, aguardar, executar ele está. A conciliação é por tributo: o IBS e a CBS são confirmados por órgãos diferentes, em momentos diferentes, e cada um tem o seu registro fiscal (RN-ING-06). Um status único não consegue dizer que o IBS fechou e a CBS ainda está aguardando.

Mesmo vocabulário da tela

As duas camadas são as da aba de eventos fiscais no documento e do modelo de ação do dossiê. O ERP lê pela API o que o operador vê na tela — com os mesmos nomes.

8.1 A fase da ação — action.phase

phaseSignificaSaldo do produto
capturadaAceito e validado, ainda sem correlação com o documentointacto
aguardando_documentoO DF ainda não chegou — fila de correlação. Reavaliado quando o documento entrarintacto
planejadaLigado ao documento e aos itens, com o efeito previsto calculado por item e por tributointacto — o previsto vem à parte
aguardando_fiscoEsperando a próxima coleta refletir o efeito em pelo menos um tributointacto, ou alterado só no tributo já executado
executadaTodos os tributos com efeito confirmaramalterado
divergenteAlgum tributo moveu em valor diferente, ou não moveu quando deveriaintacto no tributo divergente; ocorrências abertas
nao_atribuivelMais de um evento no mesmo DF dentro da janela: o delta fecha em montante, sem imputação por eventoalterado no total; uma ocorrência aberta
canceladaChegou um cancelamento válido antes da execuçãointacto — nada a desfazer
revertidaChegou um cancelamento válido depois da execuçãovolta ao anterior
Cancelada e revertida não são a mesma coisa

Para quem integra, as consequências são opostas. Em cancelada, o saldo nunca mudou e o ERP não tem nada a ajustar. Em revertida, o saldo mudou e voltou — e o ERP que já tinha contabilizado o efeito precisa estornar. A v1.0 tinha um cancelado só, e ele não dizia qual dos dois casos tinha acontecido.

8.2 A conciliação por tributo — reconciliation.ibs e reconciliation.cbs

statusQuandoAbre ocorrência?
aguardandoAinda dentro da janela — até 8 dias na CBS, até o próximo arquivo Delta no IBSNão
conciliadoO delta do órgão bateu com o previstoNão
divergenteO órgão moveu, em valor diferente do previstoSim — evt_valor_divergente
sem_reflexoA janela fechou e o órgão não moveu o que o evento prometiaSim — evt_nao_refletido
nao_atribuivelO montante fecha, a imputação não — na prática, só na CBSSim, uma só para todos os eventos da janela — evt_nao_atribuivel
sem_saldo_a_moverO evento não promete delta: 112150, 211130, 212110, 212120, 412120, 412130Não. A confirmação é por conferência própria — dossiê 7.3
nao_aplicavelO evento não toca aquele tributo. Exemplo: presumido com ind_gCBSCredPres = 0Não
A regra que impede o falso positivo

Ausência de movimento só é divergência quando o evento prometia movimento. Sem sem_saldo_a_mover, os seis eventos que o saldo não confirma nunca chegariam a executada pela API: ficariam em aguardando_fisco para sempre, ou cairiam em sem_reflexo quando a janela fechasse — doze ocorrências falsas por documento.

8.3 Como a fase deriva dos dois tributos

A fase não é um terceiro dado que pode discordar dos outros dois: ela é calculada a partir deles, nesta ordem.

#CondiçãoFase
1Chegou cancelamento válidocancelada se nada executou; revertida se algum tributo já executou
2Algum tributo em divergente ou sem_reflexodivergente
3Algum tributo em nao_atribuivelnao_atribuivel
4Algum tributo em aguardandoaguardando_fisco
5Todos em conciliado ou nao_aplicavelexecutada
6Evento dos seis de sem_saldo_a_moverDecidida pela conferência própria do dossiê 7.3, não pelas colunas. O 212110 e o 212120 ficam em aguardando_fisco até a decisão do Fisco, o 412120 ou o 412130

A execução é por tributo. Quando o IBS confirma e a CBS ainda aguarda, o efeito do IBS já é aplicado — reconciliation.ibs.executed_at vem preenchido — e a fase fica em aguardando_fisco. Segurar o IBS confirmado até a CBS chegar faria o saldo do produto discordar do extrato do Comitê Gestor sem motivo.

8.4 A resposta completa

O GET /v1/eventos-fiscais/{id} e o data dos webhooks carregam o mesmo objeto. O exemplo é o 211110 do item 7 que aparece na aba do documento: o IBS divergiu, a CBS é vedada pelo código de presumido.

8.5 Webhooks

Três eventos, no envelope que a API já usa — event, created_at, data. O data é o objeto da seção 8.4 inteiro, no estado do momento do disparo.

EventoQuando dispara
evento_fiscal.correlacionadoA fase chegou a planejada: o evento encontrou o documento e o efeito previsto está calculado
evento_fiscal.conciliadoA fase chegou a executada: todos os tributos com efeito confirmaram
evento_fiscal.divergenteA fase chegou a divergente ou nao_atribuivel. Vai junto a lista inconsistencies — uma por tributo divergente, com o previsto e o observado
Depende da decisão D-01

O produto emite hoje credito.registrado, apropriado, utilizado e glosado; o contrato público define credito.status_alterado e debito.status_alterado. Os dois contratos convivem sem decisão desde a auditoria. Os três nomes acima seguem o padrão do contrato público, mas não devem ser publicados antes de D-01 — ou nascem já em conflito. Ver D-01 na auditoria.

09Erros e lote

Resposta individual, 202, no formato que a ingestão de DFs já usa:

{
  "id": "evt_9c41b7de",
  "type": "apropriacao_credito_presumido",
  "event_code": "211110",
  "access_key": "4126…6789",
  "action": { "phase": "capturada" },     // ou "aguardando_documento", se o DF não chegou
  "created_at": "2026-09-25T13:02:11.000Z"
}

No lote, o que vale é a recusa item a item: um evento inválido não derruba os outros 499.

{
  "batch_id": "evtbatch_3k9m2x",
  "status": "processing",
  "total_events": 500,
  "accepted": 498,
  "rejected": 2,
  "events": [
    { "index": 0, "id": "evt_9c41b7de", "status": "accepted", "phase": "capturada" },

Aviso sem recusa. Um código que a NT eliminou entra, pela AE-05, com 202 e um bloco de avisos. Ele fica em capturada e não ganha ação planejada:

{
  "id": "evt_4f02aa91",
  "event_code": "211120",
  "action": { "phase": "capturada" },
  "warnings": [
    { "code": "event_code_retired",
      "message": "Evento eliminado na NT 2025.002-RTC v1.50; registrado sem ação planejada" }
  ]
}

No lote, status diz só se o item foi aceito ou recusado; a situação do evento é a phase. A v1.0 usava status para as duas coisas. O objeto de erro — code, message, field — é proposta desta página: a documentação pública atual não publica formato de erro. Se houver um padrão interno, ele manda.

v1.3

AE-05: código eliminado entra com aviso — a V-01 passa a separar código que nunca existiu de código aposentado, e a resposta ganha warnings. AE-07: tipo retirado do catálogo. Pela D-22, inconsistencies deixa de ser por item: uma por tributo, por evento, e o campo item_number sai do objeto da ocorrência. Corrigida a lista do formato items, que incluía o 112130 — ele usa items_with_reversal, como a seção 06 já dizia.
v1.2
30/09/2026 — AE-06 decidida pela D-21: esta API é a única porta de entrada dos eventos, e o cliente envia a partir do ERP e do sistema fiscal. A seção 01 passa a dizer de onde vem cada série. Corrigida a contagem de decisões em aberto: 19 na análise de impacto e 25 no módulo, e não 13 e 20.
v1.1
30/09/2026 — A situação do evento passa a ter duas camadas. O status único da v1.0 vira a fase da ação — nove fases, com planejada e aguardando_fisco no meio e cancelado dividido em cancelada e revertida, que têm consequências opostas para o ERP — e a conciliação por tributo, com sete estados, entre eles sem_saldo_a_mover e nao_aplicavel. Sem o primeiro, os seis eventos que o saldo não confirma nunca chegariam a executada. A fase deriva dos dois tributos por uma ordem de precedência, e a execução é por tributo. A resposta ganha planned_effect, o previsto, nunca somado ao vigente; reconciliation, com previsto e observado lado a lado; e inconsistencies como lista, uma por divergência por tributo e por item. O status do lote passa a dizer só se o item foi aceito. Os filtros da listagem acompanham. Nova decisão AE-07, sobre um tipo do catálogo de eventos que ficou redundante. Mesmo vocabulário da aba de eventos no detalhe do documento.
v1.0
25/09/2026 — Primeira proposta. Seis rotas, um envelope com discriminador, oito formatos de detail para os dezesseis tipos, treze validações de entrada, sete estados de ciclo de vida, três webhooks e seis decisões em aberto. Baseada na NT 2025.002-RTC v1.51 e nas convenções da API pública em vigor.
