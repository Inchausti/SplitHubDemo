01Contexto e posicionamento

1.1 O problema que o módulo resolve

Todo valor que a plataforma calcula tem origem num documento fiscal. O crédito de IBS/CBS não é inferido: ele é lido de um DF que precisa existir na base, íntegro e único.

O módulo é o funil por onde tudo passa — e por isso é também o ponto onde uma falha se propaga mais longe. Documento não ingerido é crédito que nunca existiu; documento ingerido em duplicidade é crédito contado duas vezes.

O maior efeito cascata do produto

J-01 existe para que a ingestão funcione. J-04 trabalha sobre o que ela cria. J-03 só recebe a nota porque o método do contrato foi aplicado aqui. J-05 trata exatamente o que ela recusou.

Nenhum outro módulo tem esse alcance, e nenhum outro falha tão silenciosamente: um DF que não chegou não aparece em lugar nenhum como ausência.

1.2 De documento fiscal a registro fiscal

A ingestão não guarda o documento: ela o decompõe. Cada DF gera Registros Fiscais — tipicamente dois, um de IBS e um de CBS — e é o RF, não o documento, que percorre o resto da plataforma.

DF (NF-e, chave de 44 dígitos) │ ├─ RF · IBS → crédito estadual e municipal └─ RF · CBS → crédito federal │ ├─ método do contrato vigente na data de emissão │ RAD → entra na fila de Pagamentos │ Split → retido na liquidação │ Fornecedor → recolhido pelo emitente │ └─ conciliação e apropriação

03Escopo e recorte do módulo

3.1 Fontes de ingestão

Upload de XML / ZIPInterface web, arrastar e soltarSob demandaNão implementado
SFTPDiretório monitoradoLoteNão implementado
A emissão de credencial fechou o vão da ingestão por API

O contrato da API sempre existiu no papel, mas o processo de geração das credenciais não era especificado — cada cliente era integrado por um caminho manual, fora do produto.

O módulo de Integrações passou a emitir client_id e client_secret com escopos dfs:write e dfs:read, e a mostrar o curl da primeira chamada. É o canal que torna o upload manual uma exceção, não a regra.

3.2 Tipos de documento

A API publicada aceita 14 modelos de DF-e: NF-e, NFC-e, CT-e, CT-e OS, BP-e, MDF-e, GTV-e, NFCom, NF3-e, NFAg, NFGás, NF-e ABI, NFS-e e NFS-e Via.

3.3 A chave de acesso

cUF(2) AAMM(4) CNPJ(14) mod(2) serie(3) nNF(9) tpEmis(1) cNF(8) cDV(1) └──────────────────────── 44 dígitos ────────────────────────┘

É a identidade do documento e a chave de unicidade da plataforma. Para NFS-e a chave é municipal, com formato variável por provedor; NFCom e NF3-e têm estrutura própria conforme ato normativo setorial.

04Modelo de dados

4.1 Documento ingerido

{ id: 0, chave: "3526...", // 44 dígitos tipo: "NF-e Entrada" | "NF-e Saída" | ..., // Emitente emitente: "Ferroplex Mineração S.A.", cnpj: "28.447.821/0001-35", ie: "9029-6", uf: "PR", // Destinatário cnpjDest: "54.891.237/0001-48", nomeDest: "Induspar Tecnologia S.A.", // Identificação e valores cfop: "1102", serie: "001", numero: "12345", natOp: "Compra para industrialização", valor: 5132777.00, ibs: 434981.00, cbs: 347984.00, dataEmissao: "2026-09-08", // fato gerador dataIngestao: "08/09/2026 14:51", status: "importado" | "inconsistencia", validacoes: [ /* quatro verificações — ver 5.2 */ ], valLayout: true, valValidade: true, valDados: true }

4.2 Layout do CSV posicional

Dezesseis colunas separadas por ponto e vírgula, a primeira linha ignorada como cabeçalho. Linhas com menos de 13 colunas são recusadas com o número da linha.

#ColunaObrigatóriaObservação
0chavesimChave de acesso
1tipo_dfnãoPadrão NF-e Entrada
2–5cnpj_emit, ie_emit, uf_emit, nome_emitnãoNome padrão Emitente não informado
6–7cnpj_dest, nome_destnão—
8–11cfop, serie, numero, nat_opnãoCFOP padrão 1102, série 001
12valor_totalsimDeve ser numérico e maior que zero
13–14valor_ibs, valor_cbsnãoZero quando ausente
15data_emissaonãoAceita DD/MM/AAAA ou AAAA-MM-DD

A conversão numérica remove o separador de milhar e troca a vírgula decimal por ponto — o formato brasileiro é o esperado no arquivo.

05Pipeline e máquinas de estado

5.1 O pipeline em cinco etapas

① Recebimento ERP · Upload · CSV │ ② Triagem modelo identificado pelo cMod ou pela tag raiz do XML │ ③ Val. Layout schema XSD, namespace, encoding, tags obrigatórias, assinatura │ ④ Val. Dados integridade dos campos, unicidade da chave, CNPJ na Receita │ ⑤ Importado Registro Fiscal criado · segue para a apuração
EtapaVerificaRecusa por
② TriagemModelo do documento e versão do schemaTipo desconhecido ou schema incompatível
③ LayoutXSD 4.00 para NF-e, 3.00 para CT-e, ABRASF 1.00 para NFS-e; namespace, UTF-8, tags <infNFe>, <emit>, <dest>, assinatura xmldsigFalha de schema, namespace, charset ou assinatura
④ DadosChave de 44 dígitos única na plataforma, CNPJ do emitente ativo na Receita, campos obrigatórios presentesDuplicidade, CNPJ inexistente, campo ausente, alíquota inválida
O pipeline descreve a ingestão por API, não o upload CSV — ver DEF-01

O upload manual valida apenas o que o parser consegue ver: contagem de colunas, valor numérico maior que zero e formato da data. Depois disso, todo documento carregado é marcado como importado, com as quatro verificações artificialmente bem-sucedidas.

Chave de 44 dígitos, unicidade e situação do CNPJ não são verificadas no upload. Carregar duas vezes o mesmo arquivo cria documentos duplicados sem nenhum aviso.

5.2 As quatro verificações registradas

VerificaçãoCategoriaO que atesta
Schema XMLlayoutEstrutura válida conforme o XSD do modelo
Campos obrigatórioslayoutTodos os campos exigidos presentes
CNPJ emitentedadosCNPJ ativo e regular na Receita Federal
Chave de acessodadosChave única na plataforma

Cada documento carrega as quatro, com resultado e mensagem. É essa lista que o modal de detalhe apresenta, e dela derivam os três indicadores de coluna valLayout, valValidade e valDados.

5.3 Status do documento

importado As quatro verificações passaram. O Registro Fiscal foi criado e segue para a apuração.
inconsistencia Ao menos uma verificação falhou. O documento fica retido e a ocorrência vai para o módulo de Inconsistências.
Dois estados, não cinco

A v1.5 simplificou deliberadamente a máquina: o que importa operacionalmente é se o documento entrou ou não. As etapas do pipeline continuam existindo como diagnóstico — dizem onde falhou —, mas não como estados persistidos.

07Funcionalidades detalhadas

Sete funcionalidades compõem o módulo.

F-01 Listar documentos ingeridos, com paginação #t-ingestao

Um documento por linha, com identificação, valores, datas, o resultado das três categorias de validação e o status. A listagem é paginada, com navegação para a página anterior e a próxima.

A paginação é reposicionada na primeira página sempre que um filtro muda — sem isso, filtrar estando na página 7 devolveria uma tela vazia.

F-02 Buscar e filtrar #ing-busca

Busca livre combinada com cinco recortes: tipo de documento, status, resultado de validação e faixa de data de emissão (de/até).

O botão de limpar zera os seis campos de uma vez e devolve a listagem completa — operação que importa quando o recorte acumulado deixa de ser óbvio.

F-03 Importar por upload de CSV ingUploadAbrir

Modal com área de arrastar e soltar, ou seleção de arquivo. O conteúdo é lido no navegador, analisado linha a linha e apresentado em pré-visualização antes de confirmar.

O que o parser recusa

  • Linha com menos de 13 colunas — reportada com o número da linha e a contagem encontrada
  • valor_total não numérico ou menor ou igual a zero — reportado com o valor original

As demais colunas têm padrão e não bloqueiam. A data aceita os dois formatos usuais e é normalizada para AAAA-MM-DD.

A pré-visualização é o único controle antes da carga — ver DEF-01

Confirmado o upload, os documentos entram como importado sem passar pelo pipeline. Não há verificação de chave, de unicidade nem de CNPJ.

F-04 Confirmar a carga ingUploadConfirmar

Os documentos são inseridos no topo da base, os identificadores são reindexados, os KPIs e a listagem são redesenhados, e um aviso confirma quantos entraram.

A data de ingestão é carimbada no momento da confirmação, com precisão de minuto — é ela que separa quando o fato gerador ocorreu de quando o documento chegou.

F-05 Abrir o detalhe do documento abrirIngModal

Modal com o documento completo: chave, identificação, emitente e destinatário, valores decompostos em IBS e CBS, e as quatro verificações com resultado e mensagem.

Para o documento recusado, é a mensagem da verificação que diz o que falhou — estrutura XML, CNPJ não localizado, campo ausente, duplicidade, rejeição da SEFAZ ou alíquota inválida.

F-06 Apresentar o pipeline no dashboard aba Dashboard

As cinco etapas com a contagem de documentos em cada uma, e as recusas separadas por categoria: layout, dados, duplicidade e rejeição.

Três dos quatro contadores de recusa são fixos em zero — ver DEF-02

Apenas o contador de falha de layout recebe valor. Erro de dados, duplicidade e rejeição exibem zero independentemente da base, o que faz o pipeline sugerir que só existe um tipo de falha.

F-07 Consolidar os KPIs da carga _renderKPIs

Cinco indicadores recalculados a cada carga e a cada render. A taxa de sucesso é a razão entre importados e total, arredondada — o número que responde “a carga foi boa?” antes de qualquer detalhe.

O KPI de duplicados nunca contou nada

O valor é atribuído literalmente como zero, e não deriva da base. Como o upload também não verifica unicidade, o produto não tem hoje nenhum mecanismo que detecte chave repetida — e crédito contado duas vezes é o erro mais caro que a ingestão pode produzir.

10Regras de negócio
IDRegraRazão

13.1 Contrato de entrada

POST https://api.splithub.com.br/v1/documentos-fiscais Authorization: Bearer {access_token} // escopo dfs:write { type: "nfe", model: "55", access_key: "3526...", identification: { /* número, série, emissão */ }, emission: { /* CNPJ, razão social, UF do emitente */ }, destination: { /* CNPJ, nome, UF do destinatário */ }, items: [{ tax: { ibs_cbs: { /* CST, classificação, base, IBS, CBS */ } } }], total: { /* consolidado, com totais de IBS e CBS */ }, contract_id: "CT-0011" // opcional } → 202 Accepted · { id, status: "processing" }

O grupo items[].tax.ibs_cbs é obrigatório desde 01/01/2026. Documento já completed não aceita alteração — só pending ou error admitem PATCH.
